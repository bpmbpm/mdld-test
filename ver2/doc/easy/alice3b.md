## 1

Ваше предложение — публиковать онтологию напрямую в GitHub-репозитории — абсолютно верное. Для **человека** это решает проблему переходов по якорям, а для **машин** есть отдельный, не менее важный нюанс, который тоже можно решить. Давайте разберём оба аспекта.

---

### 👤 Для человека: переход по якорям в GitHub

GitHub **автоматически создаёт `id` для каждого заголовка** при рендеринге Markdown. Это означает, что ссылка вида:

`https://github.com/bpmbpm/onto/blob/main/ver1/ontology1.md#персона`

…действительно **сработает** — браузер загрузит страницу и проскроллит до нужного раздела.

#### ⚠️ Но есть важный нюанс: алгоритм генерации `id`

GitHub преобразует текст заголовка в `id` по своему собственному алгоритму, который **не описан ни в одной спецификации Markdown**. Правила такие:
- текст приводится к нижнему регистру,
- удаляются все знаки пунктуации,
- пробелы заменяются на дефисы,
- добавляется число, если нужно избежать дублирования.

**Пример:**
- Заголовок `## Персона` → `id="персона"` → ссылка `#персона`
- Заголовок `## Почтовый адрес` → `id="почтовый-адрес"` → ссылка `#почтовый-адрес`
- Заголовок `## Ontology Class` → `id="ontology-class"`

Проблема в том, что для **русскоязычных заголовков с заглавными буквами** алгоритм может работать неочевидно. Например, `## Тип` → `id="тип"`, но `## Тип Данных` → `id="тип-данных"`. Чтобы не угадывать, **лучше использовать явные HTML-якоря**:

```markdown
<a id="персона"></a>
## Персона
```

Тогда ссылка `#персона` гарантированно сработает, независимо от того, как GitHub преобразует заголовок.

#### 💡 Альтернатива: `{#custom-name}`

Некоторые платформы поддерживают синтаксис `## Заголовок {#custom-name}` для явного указания `id`. Однако **GitHub этот синтаксис не поддерживает** — он просто отобразит `{#custom-name}` как часть текста заголовка. Поэтому на GitHub остаётся только вариант с `<a id="...">`.

### 🤖 Для машин: доступ к онтологии по raw-URL

Здесь ваше предложение также работает, но требует **другого URL**. Когда RDF-парсер (Protégé, Apache Jena, GraphDB) или SPARQL-клиент пытается загрузить онтологию по ссылке:

`https://github.com/bpmbpm/onto/blob/main/ver1/ontology1.md`

…он получает **HTML-страницу** с интерфейсом GitHub, а не чистый RDF-файл. Парсер попытается распарсить HTML как Turtle и **потерпит неудачу**.

#### ✅ Решение: raw-URL

Для машинного доступа нужно использовать **raw-URL**, который возвращает **точное содержимое файла**:

```
https://raw.githubusercontent.com/bpmbpm/onto/main/ver1/ontology1.md
```

Этот URL возвращает именно тот текст, который вы записали в файле, без HTML-обёртки. Именно его следует использовать в:
- `owl:imports` при импорте онтологии,
- SPARQL-запросах (`FROM <...>`),
- конфигурациях Protégé, Jena и других инструментов.

#### ⚠️ Ограничение: Content-Type остаётся `text/plain`

GitHub отдаёт raw-файлы с заголовком `Content-Type: text/plain` (или `application/octet-stream`), а не с `text/turtle`. Строго говоря, это нарушение спецификации, но **большинство RDF-инструментов это игнорируют** — они просто пытаются распарсить содержимое как Turtle, и это работает, если файл содержит корректный Turtle.

Однако некоторые строгие клиенты могут отказаться загружать онтологию, ожидая правильный `Content-Type`. В этом случае потребуется **промежуточный сервис** (например, w3id.org), который умеет content negotiation.

### 🔗 Итоговая схема

| Аудитория | URL для использования | Что получает |
|---|---|---|
| **Человек (браузер)** | `https://github.com/bpmbpm/onto/blob/main/ver1/ontology1.md#персона` | HTML-страница GitHub + переход к якорю |
| **Машина (RDF-парсер)** | `https://raw.githubusercontent.com/bpmbpm/onto/main/ver1/ontology1.md` | Точный текст файла (Turtle) |
| **Машина (строгий клиент)** | `https://w3id.org/bpmbpm/onto/ver1/ontology1.md` | Content negotiation → `text/turtle` |

Для **человеческих** ссылок достаточно вашего предложения. Для **машинных** — используйте raw-URL или настройте w3id.org, если нужен content negotiation.

### 📝 Синтаксис заголовка в Markdown

В файле `ontology1.md` заголовки должны быть записаны **с пробелом после решётки**:

```markdown
## Персона
## Почтовый адрес
## Тип
```

**Неправильно** (не распознаётся как заголовок):

```markdown
##Персона
```

Если написать `##Персона` без пробела, GitHub не создаст заголовок и, соответственно, не сгенерирует якорь. Это, вероятно, и есть причина, по которой переход не работает.

### 🔗 Как формируется якорь

GitHub автоматически генерирует `id` из текста заголовка по алгоритму:
- приводит к **нижнему регистру**,
- заменяет **пробелы на дефисы**,
- **удаляет** знаки пунктуации,
- для кириллицы сохраняет буквы как есть.

Примеры:

| Заголовок в файле | Сгенерированный `id` | Ссылка в URL |
|---|---|---|
| `## Персона` | `персона` | `#персона` |
| `## Почтовый адрес` | `почтовый-адрес` | `#почтовый-адрес` |
| `## Тип данных` | `тип-данных` | `#тип-данных` |

**Важно:** в URL фрагмент пишется **без пробела** — `#персона`, а не `# персона`. Пробел в URL либо игнорируется, либо превращается в `%20`, что ломает переход.

### ✅ Правильная ссылка

```
https://github.com/bpmbpm/onto/blob/main/ver1/ontology1.md#персона
```

Здесь:
- В файле: `## Персона` (с пробелом после `##`).
- В URL: `#персона` (нижний регистр, без пробела).

### 🛠️ Если всё равно не работает: явные HTML-якоря

Кириллические якоря иногда ведут себя нестабильно в GitHub (особенно при смешанном регистре или спецсимволах). Самый надёжный способ — **явно задать `id` через HTML**:

```markdown
<a id="персона"></a>
## Персона

Класс, представляющий человека.

<a id="почтовый-адрес"></a>
## Почтовый адрес

Класс для описания адреса.
```

Тогда ссылка `#персона` гарантированно сработает, независимо от того, как GitHub обработает заголовок. Этот приём работает и на GitHub Pages, и в любом другом Markdown-рендерере, поддерживающем HTML.

### 💎 Итог

| Проблема | Решение |
|---|---|
| `##Персона` без пробела | Писать `## Персона` (с пробелом) |
| Якорь не находится | Использовать `#персона` (нижний регистр, без пробела) |
| Кириллица нестабильна | Добавить `<a id="персона"></a>` перед заголовком |

## 3
Чтобы якорь сработал нужно в строку браузера подставлять https://github.com/bpmbpm/onto/blob/main/ver1/ontology1.md#%D0%BF%D0%B5%D1%80%D1%81%D0%BE%D0%BD%D0%B0

Да, вы абсолютно правы. Проблема именно в **URL-кодировании кириллицы**. Когда браузер видит в адресной строке кириллические символы после `#`, он не всегда корректно сопоставляет их с `id` в HTML. А когда вы вставляете **percent-encoded** версию (`%D0%BF%D0%B5%D1%80%D1%81%D0%BE%D0%BD%D0%B0` = `персона`), браузер декодирует её в те же самые символы, но уже на уровне протокола HTTP — и переход срабатывает.

### 🔍 Почему так происходит

По стандарту RFC 3986 фрагмент URL (часть после `#`) может содержать только символы из набора `unreserved` (латиница, цифры, `-._~`) и `percent-encoded` последовательности. Кириллица в «сыром» виде формально не разрешена, хотя современные браузеры её часто принимают. Но **GitHub** и промежуточные слои (CDN, прокси) могут обрабатывать её по-разному — отсюда нестабильность.

Когда вы вставляете `#%D0%BF%D0%B5%D1%80%D1%81%D0%BE%D0%BD%D0%B0`, браузер сначала декодирует это в `#персона`, а затем ищет элемент с `id="персона"`. Это работает надёжно, потому что percent-encoding — единственный «легальный» способ передать кириллицу в URL.

### 🛠️ Как с этим работать

**Вариант 1. Всегда использовать percent-encoded ссылки**

Это работает, но выглядит некрасиво и неудобно для ручного ввода. Вы можете генерировать такие ссылки автоматически:

```js
// JavaScript: получить percent-encoded якорь
const anchor = encodeURIComponent('персона');
// → "%D0%BF%D0%B5%D1%80%D1%81%D0%BE%D0%BD%D0%B0"
const url = `https://github.com/bpmbpm/onto/blob/main/ver1/ontology1.md#${anchor}`;
```

**Вариант 2. Использовать латинские `id` для якорей**

Самый надёжный и удобный способ — оставить в URL **латиницу**, а кириллицу — только в отображаемом тексте. Явные HTML-якоря позволяют это сделать:

```markdown
<a id="person"></a>
## Персона

Класс, представляющий человека.

<a id="postal-address"></a>
## Почтовый адрес

Класс для описания адреса.

<a id="type"></a>
## Тип

Указывает, что ресурс является экземпляром класса.
```

Тогда ссылки становятся читаемыми и работают без кодирования:

```
https://github.com/bpmbpm/onto/blob/main/ver1/ontology1.md#person
https://github.com/bpmbpm/onto/blob/main/ver1/ontology1.md#postal-address
https://github.com/bpmbpm/onto/blob/main/ver1/ontology1.md#type
```

**Преимущества:**
- Не нужно percent-encoding.
- Ссылки стабильны при любых изменениях текста заголовка.
- Работают во всех браузерах и на всех платформах.
- Совместимы с RDF-префиксами: `rdf2ru:person`, `rdf2ru:postal-address`.

**Недостатки:**
- `id` не совпадает с отображаемым текстом (но это нормальная практика — например, в HTML `<h2 id="person">Персона</h2>`).

**Вариант 3. Компромисс: транслитерация**

Если вы хотите, чтобы `id` был «похож» на русское слово, используйте транслитерацию:

| Русское слово | Транслит `id` | Ссылка |
|---|---|---|
| Персона | `persona` | `#persona` |
| Почтовый адрес | `pochtovyi-adres` | `#pochtovyi-adres` |
| Тип | `tip` | `#tip` |
| Подкласс | `podklass` | `#podklass` |

Это тоже латиница, но ближе к исходному слову.

### 📊 Сравнение вариантов

| Вариант | Читаемость URL | Надёжность | Совместимость с RDF |
|---|---|---|---|
| Кириллица `#персона` | Высокая | ❌ Нестабильно | ✅ Да |
| Percent-encoded `#%D0%BF...` | ❌ Низкая | ✅ Высокая | ⚠️ Неудобно |
| Латиница `#person` | Высокая | ✅ Высокая | ✅ Да |
| Транслит `#persona` | Средняя | ✅ Высокая | ✅ Да |

### 💡 Рекомендация

Для онтологии с русскоязычными терминами **лучший вариант — латинские `id`** (вариант 2). Это даёт:
- Читаемые URL без кодирования.
- Стабильность при редактировании текста.
- Совместимость с RDF-префиксами (`rdf2ru:person`, `rdf2ru:postal-address`).
- Работу во всех браузерах и инструментах.

При этом **отображаемый текст заголовка остаётся русским** — читатель видит «Персона», а машина получает `id="person"`.

Если вы хотите, чтобы `id` всё же был на кириллице, придётся либо всегда использовать percent-encoding, либо смириться с нестабильностью. Первое работает, но неудобно; второе — не работает.
